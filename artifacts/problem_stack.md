# Problem stack

Opened 2026-09-19. Every problem detected from this date until the release that empties it.
Companion to `artifacts/todo_stack.md`: the todo stack holds work that was planned, this holds
defects, contradictions and unknowns that were found. A problem may become a todo item; it is
not deleted when it does, it is dispositioned to the item that answers it.

## The rule

A release requires this file to hold no `BLOCKER` problem. It does **not** require the file to be empty. `AGENTS.md` §11 carries the rule, the reasoning for it and the blocker predicate, and is authoritative; this file routes to it and does not restate it. Ruled 2026-09-21.

Every open row therefore carries a **release disposition** -- `BLOCKER`, `DEFERRED->0.2.7` or `ACCEPTED` -- alongside the lifecycle disposition below. The two are different questions: the lifecycle disposition says whether the problem has been answered, and the release disposition says whether this release waits for it.

**Four** lifecycle states exist and **three** of them close a problem -- `AGENTS.md` §2 names those three as repairing, accepting with a reason, or showing the premise false. `open` is listed first because it is the state they close *from*; calling it a closing disposition was this file contradicting both itself and §2 (recorded as P-69):

| Disposition | Meaning |
|---|---|
| `open` | Not yet answered. Blocks the release only if its release disposition is `BLOCKER`. |
| `repaired` | Fixed, with the commit and the check that would catch its return. |
| `accepted` | Real, not repairable, and the reason is recorded. A published artifact cannot be un-published. |
| `not-a-defect` | Investigated and the premise is false. The evidence that killed it is recorded. |

`accepted` is the dangerous one. It closes a problem without fixing it, so it carries a reason
that would survive someone hostile reading it, and it is never used for something merely
inconvenient to repair.

The closure pass is a fixpoint, ruled 2026-09-21 and narrowed from the 2026-09-19 form: the
release opens when one independent pass over the documentation, the code and both stacks finds
no new *release-blocking* problem. A new non-blocking observation is recorded and carried
forward without re-opening the cycle; a new blocker re-opens it. The earlier rule required the
pass to find nothing at all, which made every act of discovery postpone the release it was
meant to qualify.
