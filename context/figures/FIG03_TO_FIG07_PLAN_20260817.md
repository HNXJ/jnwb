## 3. The cross-cutting issue that touches fig03 *and* fig07 directly: O++ = 52 or O++ = 15?

fig03's current inline definition (`attach_template_corr_oplusplus`, corrected this week):
r≥0.65 template correlation, restricted to V4/TEO/FEF/PFC → **52 unique units**.

fig07's O++ group (2026-08-06 relayout, per its own README): **15 units corpus-wide**, split
out of the O+ group for the GLMM's functional-group factor.

These are almost certainly two different vintages of the same underlying template-correlation
method — fig07 predates fig03's r≥0.60→r≥0.65 correction and area restriction by roughly two
weeks. **Not reconciled by either figure's own code**, and each currently states its own number
without cross-referencing the other. Two options for discussion:

1. **Re-run fig07's O++ split against the current 52-unit definition** and see whether the
   GLMM's "O++ not significant, n too small (p=0.71)" result changes with the larger,
   corrected population — this is a real scientific question, not just a bookkeeping fix.
2. **Leave both as-is and state the vintage difference explicitly in both figures' captions** if
   Hamm judges fig07's headline doesn't depend on the exact O++ boundary (its main GLMM factor
   is O+ vs Null vs S+, not O++ specifically).

This is exactly the kind of same-named-different-number problem the repo audit's
[doc03](../03_classification_pipelines.md) and [doc09](../09_conflicts_and_flagged_discrepancies.md)
catalogue at the classification-table level — this is its concrete instance inside the figure
pipeline itself.

## 4. Confirmed bugs, not yet fixed

### 4.1 fig03's stats step crashes after the SVG is written

`chi2_contingency` hits a zero-expected-frequency cell in panel e's contingency table
(`table8`/`class8()`, a legacy Q1-based codepath untouched by this week's O++ correction —
confirmed via code tracing, not a side effect of the recent edits). `fig03.svg` itself still
writes successfully; `fig03_stats.md`/`fig03_receipt.json` are stale relative to it. This is a
statistics-logic decision (how a degenerate contingency table should be handled — drop the
offending cell? collapse a sparse category? report the cell that's zero and why?), not a
mechanical fix, so it needs Hamm's call rather than a silent patch.

### 4.2 fig06 reads the superseded v1 TFR extraction

`fig04_v1_pfc_condition_tfr.py`'s `CONDITION_MAPS` constant points at a dead `D:/workspace/
omission/...` path that (even if the drive existed) would read the pre-corpus-migration v1
extraction, not the current canonical v2 (`outputs/condition_tfr_maps_p1d1p2d2p3_v2/maps.npz`,
per `context/PROJECT_STATE.md`, 2026-08-14). The untracked `fig04xx_3d_condition_tfr.py`
supplement already reads v2 correctly — the fix is to point the main script at the same path.
Low-risk, mechanical, but it's a live script edit and the shared-infra caveat below applies —
worth doing in its own small commit, separate from any panel-layout work.
